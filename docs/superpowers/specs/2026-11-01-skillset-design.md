# 개인 스킬셋 설계

작성일 2026-11-01. 저장소 `~/Desktop/develop/my-skills` (나중에 `ksone02/my-skills`로 공개 또는 비공개 업로드).

표기: **[결정]**은 사용자가 대화에서 정한 것, **[판단]**은 설계자가 정한 것(사용자가 읽으며 확인할 항목)이다.

## 1. 왜 만드나

지금은 Superpowers로 "기획 → 전문가 피드백 → 설계 → 피드백 → 개발 → 검증" 루프를 돌린다. 피드백은 꼭 필요하다(한 번에 끝내면 반드시 실수가 나온다). 하지만 토큰과 시간이 너무 든다. 여러 스킬셋(Superpowers, gstack, Matt Pocock, Addy Osmani, pstack, Compound, Spec Kit, toss apps-in-toss-harness, impeccable, taste-skill, hallmark, humanizer)을 읽고, 쓸 만한 절차만 골라 사용자 방식에 맞춘 플러그인 하나로 묶는다. Superpowers를 **완전히 대체**한다 **[결정]**.

### 사용자가 실제로 겪는 문제

1. 아이디어를 스스로도 구체화하지 못할 때 답답하다.
2. UX가 어떻게 해야 좋은지 직관이 없다. 그래서 레퍼런스를 찾거나, AI와 대화하거나, 페르소나·전문가 관점 피드백을 받는다.
3. 피드백 단계가 비싸다. 하지만 실제로 잡히는 실수가 있다.
   - AI가 필요한 구현을 빠뜨림
   - AI가 코드에서 논리 실수를 함
   - AI가 기획을 다르게 해석하거나 예외를 놓침
   - 그 분야 전문가여야 떠올릴 수 있는 지적(퀀트면 금융·수학·개발, 웹이면 기획·디자인·시니어 개발)
4. 리서치(웹, 논문)를 자주 맡기는데 결과가 아쉽다.
   - 탐색이 얕아 다음 분석·기획의 근거로 쓰기 어렵다
   - 단어 하나에 매몰돼 다양하게 못 찾거나 의도와 다른 걸 조사한다
   - 토큰 낭비가 심하다

### 사용자 성향 (여러 프로젝트 메모리에서)

- 하는 일 대부분이 분석·연구(공모전, 퀀트 알파 탐색)이고, 웹 대시보드·도구를 만든다. 랜딩 페이지도 가끔 만든다 **[결정]**.
- 시킨 것만 한다. 다음 단계를 알아서 시작하지 않는다.
- 결정은 하나씩, 대화로 한다.
- 예산이 적다(군 복무 중). 단순 작업은 저가 모델에, 검색은 DeepSeek(aside), 검증은 Codex에 맡겨 왔다.
- 쉬운 한국어. 숫자는 뜻·단위·계산법을 밝힌다. 비유를 지어내지 않는다.
- AI 티 나는 글과 UI를 싫어한다(왼쪽 테두리 강조 카드, 반짝이 아이콘 금지 등).
- 연구는 "항상 의심하고 검증"하고, 논문과 오픈소스를 근거로 댄다.

## 2. 목표, 하지 않을 것, 실패로 볼 것

**목표**
- 위 문제 1~4를 각각 덜어 주는 절차.
- 피드백 비용을 줄이되 실수를 잡는 능력은 유지한다.
- 개발과 연구 둘 다 다룬다. 프론트·디자인·한국어 글도 다룬다.

**하지 않을 것**
- 특정 분야(미니앱, 과금, iOS 등) 전용 스킬.
- 서버·MCP 구현. 이 플러그인은 스킬 파일과 작은 스크립트만 담는다.
- 다른 스킬셋을 통째로 복사해 넣기.

**실패로 볼 것 (돌아가더라도)**
- 스킬이 알아서 끼어들어 시키지 않은 일을 한다.
- 평소 세션에 큰 컨텍스트를 상시로 올린다.
- 피드백이 예전보다 비싸거나, 같은 양인데 덜 잡는다.
- 선택지를 늘어놓고 사용자에게 일을 되돌린다(2층 지적을 한 번에 묻는 것은 예외, 아래 4.3).
- 사용자 데이터(대회 데이터 등)를 외부 모델에 보낸다.

## 3. 제약

- **부를 때만 돈다 [결정].** 모든 스킬은 `disable-model-invocation: true`. 세션 시작 훅을 넣지 않는다. 한 스킬이 끝날 때 다음 스킬을 한 줄로 알려 줄 수는 있지만 직접 부르지 않는다. 스킬 안에서 `rules/`·`references/` 파일을 읽고 하위 에이전트·외부 CLI를 부르는 것은 허용한다. 다른 플러그인의 스킬(taste-skill, humanize-korean)은 흐름 안에서 필요하면 자동으로 부른다 **[결정]**.
- **상시 안전장치 [결정].** 흐름 스킬은 수동이지만, 부르지 않아도 지켜야 할 원칙 5~6줄은 `~/.claude/CLAUDE.md`에 넣는다(수백 토큰). Superpowers가 자동 발동으로 막던 실수를 이걸로 막는다. 내용은 `rules/always.md`가 정본이고 설치 스크립트가 CLAUDE.md에 블록으로 넣고 뺀다.
  - 완료·통과라고 말하기 전에 그 자리에서 확인 명령을 돌리고 결과를 보인다.
  - 같은 전제로 고친 게 두 번 실패하면 전제를 적고 직접 검증한다.
  - 검토 지적(Codex, 전문가 역할, 사람)은 맞는지 코드로 확인한 뒤 반영한다. 틀리면 근거를 들어 반박한다.
  - 숫자를 보고할 때 무엇을 잰 것인지, 단위, 계산법을 밝힌다.
  - 주장마다 측정함 / 추정함 / 추측을 구분하고, 읽지 않은 링크·출처는 쓰지 않는다.
  - 되돌리기 어려운 일(배포, 푸시, 외부 전송, 삭제)은 확인받는다.
- **반복되는 실수는 구조로 막는다 [판단].** 같은 지시를 두 번 쓰게 되면 훅·스크립트·린트로 옮긴다(pstack "교훈은 구조로", toss unity-sdk의 자동 생성 파일 수정 차단 훅). 플러그인에는 선택형 훅 하나만 둔다: 운영 브랜치 푸시, `rm -rf`, 비밀키 파일 읽기 같은 위험 명령에서 멈추고 확인(gstack `careful`). 기본은 꺼짐, `/my-skills:guard on`으로 켠다.
- **이름 충돌.** 플러그인 이름 `my-skills` 접두사(`/my-skills:plan`)로 부른다. Superpowers와 같은 세션에 있어도 겹치지 않는다 **[판단]**.
- **평소 비용 0 [판단].** 스킬 본문은 짧게, 긴 기준은 `references/`로 빼서 필요할 때만 읽는다(toss harness 원칙).
- **기준은 한 곳 [판단].** 글·UI·검토 규칙은 `rules/` 파일 하나씩에만 쓰고, 스킬은 가리키기만 한다.
- **데이터 안전.** 외부 모델(DeepSeek, Codex)에는 질문, 코드, 명세, 공개 문서만 보낸다. 원본 데이터, 대회 데이터, 개인 정보, 키는 보내지 않는다. 방식은 단순하게 **[판단]**:
  - 래퍼 스크립트가 보낼 파일을 고를 때 빼는 것: `data/`·`raw/`·출력 폴더, `.env*`, `*.csv`·`*.parquet`·`*.xlsx` 등 데이터 확장자, 1MB 넘는 파일, 키처럼 보이는 문자열이 든 파일.
  - 프로젝트의 `CLAUDE.md`나 메모리에 "외부 AI 금지/업로드 금지"류 문구가 있으면 외부 모델을 쓰지 않고 Claude로 넘어간다.
  - 검색 질문에는 데이터 값(행, 수치 원본)을 넣지 않는다.
  - 뺀 파일이 있으면 결과에 목록 한 줄. 사용자에게 매번 묻지 않는다.
- **같이 쓰는 설치물.** ponytail, humanize-korean, claude-mem은 그대로 둔다 **[결정]**. Superpowers는 이 플러그인이 동작을 확인한 뒤 끈다(제거 시점은 사용자가 정한다).
- **외부 도구.** `aside`(`~/.local/bin/aside`, DeepSeek 호출), `codex`(`/opt/homebrew/bin/codex`)가 설치돼 있다. taste-skill은 필요할 때 설치한다.
- **라이선스.** 참고 저장소는 모두 MIT, Apache-2.0, BSD-3. 가져온 문장이 있는 파일에는 출처를 적고 `NOTICE.md`에 원본 저작권을 모은다.

## 4. 동작 설계

### 4.1 개발 흐름

| 단계 | 스킬 | 하는 일 | 참고한 곳 |
|---|---|---|---|
| 0. 기존 코드 파악 (있는 저장소일 때) | `shape`·`plan` 첫 단계 | 관련 파일, 호출하는 곳, 관례, 테스트·린트 명령을 훑어 명세 앞에 짧게 적는다. 프로젝트 `CLAUDE.md`에 명령 요약이 없으면 추가를 제안한다(`check`가 무엇으로 검증할지 알게) **[판단]** | 공식 Feature Dev 탐색 에이전트, Matt `wayfinder`, toss es-toolkit |
| 1. 구체화 | `shape` | 아래 4.1.1 | Matt `grill-me`, toss `plan` 아이데이션, pstack `in-your-own-words`, Superpowers brainstorming |
| 2. 기준 세우기 (필요할 때만) | `research` 또는 `review --persona` | UX처럼 판단 기준이 없을 때 레퍼런스를 찾거나 페르소나 관점을 받는다 | 사용자 기존 방식 |
| 3. 전문가 검토 ① | `review` | 기획 직후. 아래 4.3 | gstack 역할 검토, Compound 검토 묶음, pstack `interrogate` |
| 4. 설계·계획 | `plan` | 작업을 독립적으로 끝나는 단위로 나누고, 위험하거나 모르는 것부터 배치. 각 단위에 완료 조건 번호를 연결. 끝나면 자기 점검: 명세 항목마다 대응 작업이 있는지, 앞뒤 작업의 이름·타입이 맞는지, 계획이 명세보다 과하게 길지 않은지, 영향받는 파일(문서, 다국어, 관련 함수)을 다 포함했는지 | Superpowers writing-plans(Self-Review), pstack `figure-it-out`, toss es-toolkit PR 리뷰 |
| 5. 전문가 검토 ② | `review` | 설계 직후, 만들기 전 | 같음 |
| 6. 구현 | `build` | 아래 4.1.2 | Superpowers subagent-driven-development, 사용자 메모리 |
| 7. 대조 검사 | `check` | 아래 4.4. 마지막에 브랜치 전체를 가장 좋은 모델로 한 번 검토 | Spec Kit `analyze`, pstack `prove-it-works`, Superpowers verification-before-completion |
| 8. 마무리 | `finish` | 실제 결과물 확인, 브랜치 정리, 커밋·PR은 사용자가 시킬 때만 | Superpowers finishing-a-development-branch |

**[판단]** 크기에 따라 단계를 건너뛴다.
- 한 파일, 뻔한 수정 → 바로 고치고 `check`만.
- 작은 변경 → `shape` 간단히 → `build` → `check`.
- 프로젝트 → 전 단계.
`shape`가 끝날 때 크기를 한 줄로 말하고, 사용자가 바꿀 수 있다.

#### 4.1.1 `shape`의 동작

1. 질문은 한 번에 하나. 열린 질문부터, 막히면 짧은 보기.
2. 아이디어가 막연하면 toss 방식으로 넓힌다.
   - 사용자 재료로 축 3개(불편했던 일, 반복하는 일, 역발상).
   - 에이전트가 혼자 후보를 지어내지 않는다.
   - 후보는 "누가, 언제, 무엇을 한다" 한 줄.
   - 실현성 질문으로 걸러 1개로 좁힌다.
3. 이해한 부분을 200~300자로 되읽어 주고 틀린 곳을 묻는다. 추측은 추측이라고 표시.
4. 예외 상황을 먼저 묻는다(빈 값, 경계값, 권한 없음, 실패 시).
5. 산출물: `docs/specs/<날짜>-<주제>.md`.
   - 목적, 하지 않을 것, 실패로 볼 것
   - **완료 조건 목록**(번호, 확인 방법 포함. 예: `D3. 1366×768에서 브리핑 패널 끝까지 스크롤된다 — 브라우저로 확인`)
   - 사용자 결정 / 에이전트 판단 구분

#### 4.1.2 `build`의 동작 (Superpowers subagent-driven-development에서)

1. **진행 기록을 먼저 연다.** `docs/progress/<날짜>-<주제>.md`. 작업마다 시작 커밋, 상태, 검토 결과, 완료 줄. 요약(컴팩트)돼도 이 파일로 이어 간다.
2. **구현자 하위 에이전트**에 작업 설명서 파일을 준다. 같은 모양의 작은 작업(같은 수정을 여러 파일에)은 하나로 묶고, 판단·테스트·검토가 따로 필요한 작업은 따로 보낸다. Agent 도구의 `model` 인자로 모델을 고른다(`agents/` 정의 없음) **[판단]**.
3. **구현자 상태 보고 4종:** 완료 / 걱정 있음(했지만 맞는지 의심) / 막힘 / 맥락 필요. 막힘·맥락 필요면 메인이 답하고 같은 구현자를 이어서 쓴다(메인이 직접 고치지 않는다, 맥락 오염 방지).
4. **작업마다 검토.** 검토자에게 diff를 파일로 넘긴다(메인 맥락에 넣지 않음). 판정 두 가지 모두 필수: 명세대로인가, 품질은 괜찮은가. 검토자에게 "이건 지적하지 마" 같은 미리 판단을 주지 않는다. 결과는 4.3의 3층으로 처리.
5. **수정 반복 상한 3회 [판단].** 넘으면 멈추고, 남은 지적을 "보류 + 이유"로 기록한 뒤 사용자에게 한 번에 보고. 4회째부터는 한 등급 위 모델로 바꾼다.
6. 모든 작업이 끝나면 `check`로 넘어간다(한 줄 안내).

### 4.2 연구 흐름 (`research`)

1. **조사 계획을 먼저 쓴다.**
   - 이 조사로 내릴 결정
   - 이미 아는 것
   - 결정을 바꿀 발견
   - 각도 4~6개(동의어, 옆 분야, 한국어·영어, 반대 입장, 원문 출처 종류)
   - 사용자에게 보여 확인받는다(1분 분량). 의도와 다르게 해석하는 일을 여기서 막는다.
2. **넓게 훑기.** 각도별로 하위 작업을 나눠 맡긴다(4.5 모델 분담). 결과는 출처가 붙은 지도: 주요 갈래, 대표 출처, 아직 빈 곳.
3. **방향 고르기.** 사용자가 파고들 갈래를 고른다.
4. **깊게 보기.** 2차 요약글이 아니라 원문(논문 본문, 인용 추적, 공식 문서, 소스 코드, 저장소). 새 출처를 봐도 새 내용이 나오지 않으면 멈춘다.
5. **결과는 파일 하나.** `docs/research/<날짜>-<주제>.md`. 주장마다 출처, 확실한 것과 추정 구분, 결정에 주는 함의. 메인 대화에는 요약만 올린다.

### 4.2.1 실험형 연구 (`experiment`)

퀀트 알파 탐색, 모델 성능 개선처럼 지표 하나를 반복 실험으로 올리는 일. pstack `hillclimb`이 바탕.

1. **목표와 지표를 적는다.** 지표, 목표값, 기준값(지금 상태), 노이즈 수준. 목표 기준은 나중에 느슨하게 바꾸지 않는다.
2. **측정 장치를 먼저 만들고 고정한다.** 차이를 잡아낼 만큼 민감한지 대조 사례로 증명한 뒤 바꾸지 않는다. 데이터 누수, 미래 정보, 과최적화(같은 평가셋으로 고르고 보고하기) 점검을 장치에 넣는다.
3. **시도 기록** `docs/experiments/<주제>/decision.tsv`: 번호, 가설, 변경, 전, 후, 차이, 판정(남김/되돌림), 메모. 시도 전마다 읽는다.
4. **한 번에 변경 하나, 측정 하나.** 가설은 구체적인 이유를 단다("X를 빼면 Y 때문에 Z가 준다"). 노이즈를 넘고 회귀 검사가 통과할 때만 남기고, 아니면 완전히 되돌린다.
5. **첫 정체에서 멈추지 않는다.** 여러 번 연속 실패하면 방향을 바꾸거나 근소하게 실패한 것들을 합쳐 본다. 싼 시도가 남았으면 그만두지 않는다.
6. 결과 보고: 기준값 → 최종값(차이), 시도 수(남김/되돌림), 남긴 변경 한 줄씩, 다음에 해 볼 것.
- 실제 시도는 하위 에이전트에 맡기고 메인은 감독·검토·기록만 한다. 데이터 안전 규칙(3장)을 그대로 지킨다.

### 4.3 전문가 검토 (`review`)

**[결정]** 피드백은 두 종류로 나눈다.
- **대조 검사**(`check`, 4.4): 싸게, 자동으로, 단계마다.
- **전문가 검토**(`review`): 비싸게, 기획 직후와 설계 직후 두 자리에서만. 개발 뒤에는 결과가 기대와 다를 때만 다시 부른다 **[판단]**.

**역할**
- 분야별 역할 정의를 `references/roles/`에 저장해 재사용한다. 파일 하나에 역할 3~4개, 역할마다 "이 역할이 꼭 보는 항목".
- 처음 만들 파일 **[판단]**: `quant.md`(금융, 수학·통계, 트레이딩 시스템 개발), `web.md`(기획, 디자이너, 시니어 프론트), `data-research.md`(통계, 도메인 전문가, 재현성 검토자).
- 역할은 한 라운드에서 병렬로 돌린다.
- 역할 선택 **[판단]**: 사용자가 `review quant`처럼 지정하면 그 파일. 지정이 없으면 명세를 보고 고르고, 고른 역할을 보고 첫 줄에 적는다(사용자가 바로 바꿀 수 있게). 맞는 파일이 없으면 그 자리에서 역할 3개를 만들어 쓰고, 끝에 저장할지 한 줄로 묻는다.

**지적의 형식과 3층 [결정]**
- 지적 하나 = 무엇이, 왜 틀렸고, 무엇을 바꾸는지 + 근거(논문, 레퍼런스, 계산, 실행 결과). 근거 없거나 막연한 지적("더 견고하게")은 버린다.
- 지적은 3층으로 나눈다(toss render-rules, hallmark Floor/Reflex/Finish).

| 층 | 뜻 | 처리 |
|---|---|---|
| 1층 하드 | 틀렸거나 사용자·데이터를 해침 | 바로 고치고 고친 내용 보고. 못 고치면 완료 아님 |
| 2층 권장 | 더 나아짐 | 번호, 근거, 고치는 비용을 한 줄씩 적어 **한 번에** 묻는다. 고른 번호만 고친다. 답이 없으면 고치지 않는다 **[판단]** |
| 3층 자유 | 취향·개성 | 지적하지 않는다 |

- 과잉 지적 금지를 역할 프롬프트에 명시한다.

### 4.4 대조 검사 (`check`)

1. 완료 조건 목록을 하나씩 대조해 통과 / 실패 / 확인 불가로 판정. 확인 불가는 통과가 아니다.
   - 입력: 사용자가 지정한 명세, 없으면 `docs/specs/`에서 가장 최근 파일.
   - 명세가 없으면(작은 작업) 요청에서 완료 조건 3~5개를 직접 만들고, 보고 맨 위에 그 목록을 적은 뒤 진행한다. 멈추지 않는다 **[판단]**.
2. 논리는 의견이 아니라 실행으로 증명한다. 깨지는 입력을 찾아 돌리고, 실행 결과로 증명된 지적만 남긴다.
3. 화면이 있으면 실제 브라우저로 연다(4.6).
4. 검사자는 **Codex**. 사용량이 없거나 실패하면 Claude 하위 에이전트로 넘어가되 독립성 조건을 지킨다 **[결정]**.
   - 메인 대화를 물려받지 않은 새 하위 에이전트
   - 기획(완료 조건)과 결과물만 주고, 만든 쪽의 생각 과정은 주지 않는다
   - 가능하면 만든 모델과 다른 등급
   - 결과에 "Codex 사용 불가, Claude로 검증" 한 줄
5. 검사 결과도 3층으로 처리한다.

### 4.5 모델 분담 [결정]

| 일 | 1순위 | 안 되면 |
|---|---|---|
| 넓게 검색, 원문 읽기 | DeepSeek via `aside -m deepseek/deepseek-v4-pro` | Claude 저가 모델(haiku 또는 sonnet) 하위 에이전트 |
| 대조 검사, 실행 검증, 반박 | Codex CLI | Claude 하위 에이전트 + 독립성 조건(4.4) |
| 전문가 역할 검토 | Claude(필요하면 Codex 1명 추가) | — |
| 구체화, 설계, 종합 | Claude 메인 | — |
| 반복 구현 | Claude 하위 에이전트(등급은 아래) | — |

- **모델 등급 [판단, Superpowers 실측 근거]:** 가장 싼 모델은 여러 단계 작업에서 턴을 2~3배 써서 총비용이 오히려 클 수 있다.
  - haiku: 계획에 쓸 코드가 다 들어 있을 때(옮겨 적기+테스트), 한 파일 기계적 수정.
  - sonnet: 설명만 보고 구현하는 작업, 여러 파일, 모든 검토자의 하한.
  - opus 이상: 설계 판단, 마지막 브랜치 전체 검토, 막혀서 올리는 수정.
  - 하위 에이전트를 띄울 때 모델을 항상 적는다. 빠뜨리면 비싼 세션 모델을 물려받는다.
- 외부 호출 결과는 같은 양식(출처가 붙은 마크다운 파일)으로 받아 메인이 같은 방식으로 읽는다.
- 대체 수단으로 넘어간 사실은 결과에 한 줄로 남긴다.
- 처음 몇 번은 같은 조사를 DeepSeek과 Claude에 같이 시켜 깊이를 비교한다 **[판단]**. 결과는 `docs/research/model-compare.md`에 남긴다.

### 4.6 디자인·프론트 (`design`, `copy`)

**[결정]** 화면 종류로 길을 나눈다.

| 화면 | 방식 |
|---|---|
| 대시보드, 도구 (주로) | `design`. impeccable의 "Operate" 모드가 바탕: 훑어보기 쉬움, 일관성, 실제 사용 장면이 표현보다 우선. 상태(빈 화면, 로딩, 에러, 비활성) 전부 |
| 랜딩, 소개 (가끔) | `design --landing`이 taste-skill을 자동으로 부른다 **[결정]**. 설치돼 있지 않으면 설치 명령을 안내한다. 라이브러리와 측정 스크립트가 핵심이라 다시 만들지 않는다 |

**공통**
- 1층 규칙은 `rules/ui.md` 하나. 처음 항목:
  - 왼쪽 테두리 강조 카드, 반짝이 아이콘, 장식용 그라데이션 금지(사용자 메모리)
  - 화면에 내부 이름(모델명, 데이터 출처 약어, "엔진" 등) 노출 금지
  - 지어낸 수치·후기·로고 금지, 모든 상호작용 요소에 포커스 표시, 가로 스크롤 금지(hallmark Floor에서 고름)
  - 색·글꼴은 토큰으로
- 2층은 impeccable craft-floor 점검 목록(대비, 그림자, 간격, 타입, 상태, 브라우저 기본 요소, 문구, 요구사항 누락)에서 고른다.
- 장식을 뺀 자리는 실질로 채운다(taste-skill의 경고: 빼기만 하면 빈약해 보인다).
- **실제 브라우저에서 잰다.** 데스크톱(1440), 노트북(1366×768), 휴대폰(390) 세 폭으로 열어 스크린샷을 찍고 비평. 최대 3번 반복 **[판단]**. 측정은 작은 스크립트(Playwright 또는 Chrome)로: 가로 넘침, 잘린 요소, 글자 크기 범위, 대비.
- 시안을 고를 때는 2~3개를 나란히 보여 준다.

**`copy` (화면 문구)**: toss `ux-writing` 절차.
1. 문구 전수 수집(화면, 위치, 원문 표)
2. 원칙별 점검
3. 수정 전후 제안
4. 승인받은 것만 반영
원칙은 `rules/writing-ko.md`를 가리킨다.

### 4.7 글 (`unslop`)

- `rules/writing-ko.md` **[판단: 처음 항목]**
  - 쉬운 말, 숫자마다 뜻·단위·계산법, 비유 금지
  - 고립 같은 민감한 주제는 개수가 아니라 상대적 경향으로
  - toss 문구 원칙: 사용자가 주어, 얻는 것으로 말하기, 확인 가능한 사실, 문장 나누기, 반복 금지, 원인과 다음 행동, 결과를 말하는 버튼, 어투 통일
  - 자리별 말투: Notion "~함" + 들여쓰기 목록 / README·화면 해요체 / 답변 짧은 한국어
- `rules/writing-en.md`: blader/humanizer가 바탕. 구조 먼저(과장, 정해진 리듬, 강조 남발, 채팅 흔적, 독자가 아는 걸 다시 설명). "남기는 문장은 독자가 몰랐던 걸 더해야 한다", "손대지 말아야 할 때".
- `unslop`은 대상 언어에 맞는 규칙으로 고친다. 한국어 긴 글은 마지막에 humanize-korean을 자동으로 부른다.

### 4.8 공통 원칙 (`rules/core.md`)

스킬마다 가리키는 짧은 원칙 모음. 처음 항목:
- 버그는 재현 장치부터 만든다(Matt `diagnosing-bugs`). 별도 스킬 `diagnose`로도 둔다.
- 같은 전제로 고친 게 두 번 실패하면 전제를 적고 직접 검증한다(pstack `attack-the-premise`).
- 숫자를 보고하기 전에 무엇을 잰 것인지, 무엇이 값을 제한하는지, 다른 무엇을 재고 있을 수 있는지 밝힌다(pstack `explain-the-number`).
- 확실하지 않은 사실은 공식 문서로 확인하고 출처를 붙인다(Addy `source-driven-development`).
- 시킨 것만 한다. 되돌리기 어려운 일(배포, 푸시, 외부 전송, 삭제)은 확인받는다.

### 4.9 인계와 결정 기록 (`handoff`)

- **멈출 때(`handoff pause`)** — pstack `pause-safely`: 안전한 지점에서 멈추고 새 일은 시작하지 않는다. 고친 파일은 `wip:` 커밋 하나로 남긴다(사용자가 커밋을 원치 않는 저장소면 패치 파일로). 재개 메모 `docs/progress/HANDOFF.md`: 목적, 하던 일, 확인된 것, 현재 상태, 다음 할 일, 주요 파일, 정한 결정.
- **이어 갈 때(`handoff resume`)** — pstack `session-pickup`: 메모와 진행 기록을 읽고, git으로 실제 상태를 맞춰 본다. 이전 세션이 "됐다"고 한 것은 실제 결과물로 다시 확인한 뒤 이어 간다.
- **결정 기록 [판단]:** 사용자가 정한 것은 `docs/decisions.md`에 한 줄씩(날짜, 결정, 이유, 대안). 팀 공유 문서(`논의_필요.md` 같은 것)가 있으면 그 파일을 쓴다. Addy `documentation-and-adrs`, pstack `show-me-your-work`.

### 4.10 보조 기법 (references, 필요한 스킬에서만 읽음)

- 디버깅: 재현 장치부터(Matt), 원인 역추적, 여러 겹 방어, 불안정한 테스트는 시간 대신 조건으로 기다리기, 다른 테스트를 오염시키는 테스트 찾기(Superpowers systematic-debugging).
- 물어보는 대신 확인하기: 실행해 보면 알 수 있는 갈림길은 작은 시제품으로 확인하고 결과를 보여 준다(pstack prototype). 취향·방향 질문만 사용자에게 묻는다.
- 읽기 전용 조사: "X는 어떻게 동작하나", "왜 이렇게 만들었나"는 코드를 고치지 않고 근거와 함께 답한다(pstack investigation).

## 5. 스킬 목록 (처음 버전)

| 스킬 | 한 줄 |
|---|---|
| `shape` | 흐릿한 아이디어 → 완료 조건 목록이 있는 명세 |
| `plan` | 명세 → 위험 먼저 배치한 작업 단위 |
| `build` | 계획을 저가 모델에 묶어 구현 |
| `check` | 완료 조건 대조 + 실행 증명 (Codex → Claude) |
| `review` | 분야별 전문가 역할 검토, 3층 처리 |
| `finish` | 마무리 확인, 브랜치 정리 |
| `research` | 조사 계획 → 넓게 → 고르기 → 깊게 → 파일 |
| `experiment` | 지표 하나를 반복 실험으로 올리기(측정 고정, 시도 기록, 남김/되돌림) |
| `handoff` | 멈추기·이어 가기, 결정 기록 |
| `guard` | 위험 명령 확인 훅 켜기/끄기(선택) |
| `diagnose` | 재현 장치부터 만드는 버그 진단 |
| `design` | 대시보드·도구 화면 만들기·고치기, 랜딩은 taste-skill로 |
| `copy` | 화면 문구 전수 점검과 재작성 |
| `unslop` | 글의 AI 티 제거(한국어·영어 규칙) |

**[판단]** 모든 스킬은 toss 형식을 따른다: 목적 / 입력 / 산출물 / 실행 순서 / 하지 않는 것 / 하지 말아야 할 것. 본문은 짧게(대략 1,500단어 이하), 나머지는 `references/`.

## 7. 잘 되는지 확인하는 법

toss harness의 두 가지 시험을 작게 따른다 **[판단]**.
1. **부르기 시험:** 각 스킬이 이름으로 불렸을 때 뜨고, 이름 없이 비슷한 요청을 했을 때 뜨지 않는지(부를 때만 도는지).
2. **압박 시험 [판단]** (Superpowers writing-skills, pstack eval): 규율형 규칙(상시 안전장치, `check`, 3층)이 "급하니 건너뛰자" 같은 압박에서도 지켜지는지. 압박 문장을 붙인 과제를 주고, 규칙을 어기면 그 핑계를 규칙 파일의 "이런 핑계는 안 됨" 표에 추가한다.
3. **비교 시험:** 같은 작은 과제 2개(작은 웹 기능 하나, 짧은 리서치 하나)를 Superpowers와 이 스킬셋으로 각각 돌려 비교.
   - 비교 항목: 끝까지 갔는지, 총 토큰, 사용자에게 되물은 횟수, 끝난 뒤 남은 실수 수(완료 조건 기준)
   - 결과는 `evals/results/`에 남기고, 이 스킬셋이 토큰은 적고 남은 실수는 같거나 적어야 Superpowers를 끈다.
   - 토큰 **[판단]**: Claude 쪽은 세션 기록(`~/.claude/projects/.../*.jsonl`)의 usage 합계. 외부 호출(Codex, DeepSeek)은 래퍼 스크립트가 호출 수·출력 길이·걸린 시간을 `evals/results/`에 기록하고 따로 적는다(합산하지 않음).
   - 한쪽만 켜기: 시험마다 새 세션에서 `/plugin disable`로 다른 쪽을 끈다.

## 8. 만드는 사람에게 맡기는 것

- 각 스킬 본문의 문장, references 분할 방식.
- 외부 모델 래퍼 스크립트의 구현(언어, 시간 제한, 실패 판정). macOS에는 `timeout`이 없으니 `perl -e 'alarm N; exec @ARGV'` 패턴을 쓴다.
- 브라우저 측정 스크립트의 도구 선택(Playwright 또는 Chrome 확장).
- 역할 파일의 세부 항목(처음 버전 뒤 사용자가 다듬는다).
- 비교 시험에 쓸 과제 구체 내용.
